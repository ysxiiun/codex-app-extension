# 菜单重启确认与 CDP 恢复修复

## Task Summary

- Goal: 修复菜单显示“等待重启确认”时，点击“确认重启 ChatGPT…”在一次执行失败后被永久锁丢弃，并让已成功拉起的新进程即使 CDP/Target 暂未就绪也能交由监控自动恢复。
- Scope: 修改 `RuntimeController` 的重启计划消费、失败协调和刷新失效机制；把 `AppModel` 的永久确认锁改为单次异步执行锁；补充菜单进行中反馈、Core/XCUITest 回归及 README 合同。
- Result: 破坏性重启仍只在独立 `NSAlert` 明确确认后执行；执行中菜单显示“正在重启 ChatGPT…”并阻止重复提交；失败后锁必定释放。terminate 失败保留原重启计划，terminate 已完成但 launch 失败时转为仅启动计划，避免重试再次终止旧 PID；新进程启动后立即消费旧确认计划，后续 CDP/Target 暂时失败由监控恢复。
- Delivery: `./install.sh` 已重新构建 Release、ad-hoc 签名、原子安装至 `/Applications/Codex App Extension.app` 并通过包体审计与冷启动存活检查；用户在安装版本上明确回复“验证通过”。
- Key Constraints: 不修改 ChatGPT 包体、账号、对话或草稿；不静默重启、不 force kill；未经用户确认不执行 terminate；自动测试不触发真实 ChatGPT 重启；不提交或推送 Git。

## State and Compatibility Decisions

- 待确认的破坏性重启计划与 CDP 是否已就绪是两个独立事实。新进程已经启动时必须消费旧 pending plan，连接失败只保留错误并交给监控重连，不能继续显示一个已经失效的重启确认。
- `isRestartConfirmationInFlight` 只覆盖一次实际 `runtime.confirmRestart()` 异步调用，使用无条件释放保证成功和失败都可收敛；它不能替代 runtime 发布的 pending 状态，也不能跨失败永久保留。
- `RuntimeController` 使用刷新 revision 使 actor 在 `await` 前启动、之后恢复的旧 `refresh` 失效，防止它覆盖确认重启产生的新 PID、端口、错误或 pending 状态。
- 执行失败要按真实进程状态协调：旧 PID 仍存在时保留原 restart plan；旧 PID 已退出且没有新进程时改为 launch-only plan；发现新进程时清理旧计划并让监控按其实际调试端口重连或重新规划。
- 保持既有安全与兼容合同：独立 App-modal `NSAlert` 是唯一破坏性入口，仍使用正常 terminate、动态 `127.0.0.1` 回环端口，`RuntimeControlling` 公共形状不变。

## Reusable Technical Memory

- 对含 actor `await` 的监控刷新，仅靠入口 guard 不足以防止旧调用恢复后写回；应为每次刷新分配 revision，并在每个挂起点返回后确认 revision 仍为当前值。
- “操作已被用户确认”“破坏性计划已执行”“新进程已启动”“CDP 已连接”“Target 已安装”必须分别建模。把它们压成一个 pending 布尔值会造成伪确认、永久 UI 锁或重复终止。
- terminate 成功而 launch 失败后，重试对象已经从 restart 变成 launch；仍保留旧 PID restart plan 会对已退出进程重复 terminate，并破坏失败恢复语义。
- 菜单防双击锁应绑定真实异步事务生命周期，并在 `defer` 中释放；业务重试资格仍以 RuntimeController 的 pending plan 为准。
- 菜单栏 XCUITest 可在 macOS 状态项 `isHittable` 误判时用元素中心坐标点击，但业务是否成功仍必须由后续菜单、警告框、确认次数和重试状态断言验证。
